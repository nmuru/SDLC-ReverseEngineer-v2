ReverseEngineer-SDLC

Guide and Tips

1. Use the main repository as the input

  • Enter the repository's main Git clone URL, such as https://github.com/org/repo.git or the standard GitHub repository URL.
  • The current V1 repository acquisition flow is designed for the main/default repository and does not yet support GitHub tree URLs for branches or tags, such as /tree/v1.
  • If you need to analyse a particular branch or tag, use the repository's supported main URL for now; branch/tag URL support is planned for a later version.

2. Start with an inexpensive model

  • You do not need a frontier model to get useful SDLC documentation; OpenRouter/free models can produce a meaningful baseline, particularly when the repository is reasonably structured.
  • The application uses repository intelligence, phase-specific research, common agent instructions, and phase/skill guidance to give the model structured evidence and a repeatable analysis process.
  • A stronger model can still produce better results on difficult repositories or phases, so model quality remains one factor in the final output.
  • Once you get a baseline, you can ask your coding agent to refine the documents, if need be.

3. Model quality and cost can be compared phase by phase

  • A practical approach is to run a baseline with a free model, review the phases, and use a stronger model only where a result needs deeper reasoning or correction.
  • For the Vercel Next.js Commerce demonstration, a paid DeepSeek V4 Flash run through OpenRouter used approximately $0.10 across 141 requests, 3.27 mn tokens , with an observed cache hit rate of approximately 75.3%.
  • These figures are a demonstration snapshot rather than a fixed cost estimate; actual cost depends on repository size, selected phases, model, prompts, caching, and provider pricing.

4. All 11 SDLC phases can be run in parallel

  • All 11 phases can be selected and run in parallel.
  • If you encounter provider rate limits, running about 3 phases at a time can make failures easier to isolate and reduce simultaneous provider load.
  • You can rerun individual phases without repeating the entire analysis.

5. Current provider support

  • In the current V1 demo, the application directly supports OpenAI and OpenRouter.
  • Other model providers can be accessed through OpenRouter where their models are available, without requiring provider-specific integration in the application.

6. Treat the output as an evidence-based starting point

  • Reverse SDLC reconstructs documentation from an existing implementation; it does not know the original team's undocumented intentions.
  • The source repository remains the primary source of truth, while generated documentation is an interpretation that should be verified.
  • When reviewing a statement, ask: “Where in the repository does this claim come from?”

7. Review before using the documentation

  • Check business behavior, architecture, technology and dependency claims, user workflows, security observations, testing claims, assumptions, and recommendations.
  • AI can miss relevant code, oversimplify architecture, infer behavior incorrectly, or describe legacy behavior as intentional design.
  • If a phase is weak, rerun that phase and, if necessary, compare the result from a stronger model.

8. Documenting an existing repository

  • Run a baseline: Start with an available inexpensive model rather than optimizing for maximum model capability immediately.
  • Review: Identify statements that are well supported, uncertain, speculative, incomplete, or incorrect.
  • Rerun: Improve weak phases individually instead of automatically rerunning everything.
  • Refine: Review and refine the generated documents before treating them as permanent project documentation.

9. Do not confuse current behavior with desired behavior

  • Reverse SDLC starts from what the software currently implements, so generated requirements and architecture may describe existing behavior even when that behavior is undesirable or incomplete.
  • When converting the output into future specifications, explicitly distinguish observed current behavior from intended future behavior.

10. Use Reverse SDLC for specification-driven development

  • Generate documentation from the implementation, review it, resolve contradictions and ambiguities, and refine it into a specification that represents the intended future system.
  • The resulting documentation can then serve as a structured input for subsequent development work, including AI-assisted specification or coding workflows.

11. When a result does not look right

  • First determine whether the problem is isolated to one phase rather than assuming the entire analysis has failed.
  • If the repository contains ambiguous, inconsistent, legacy, or undocumented behavior, human review may be required to determine the intended meaning.

12. Important limitations

  • Reverse SDLC cannot guarantee that every generated statement is correct or complete.
  • The quality of the result depends on the repository, the available repository intelligence, the analysis instructions, and the model used.
  • Generated documentation should be reviewed before it is used for important technical, product, or business decisions.

13. Practical workflow

Use the main repository → Analyze → Review → Identify weak phases → Rerun selectively → Refine → Publish/use
  • Start inexpensively, spend additional model capacity only where it improves the result, and keep the source repository available for verification.
