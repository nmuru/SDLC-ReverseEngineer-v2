ReverseEngineer-SDLC

Guide and Tips

Features at a glance

  • Comprehensive SDLC documentation: Generate a structured set of SDLC documents from an existing codebase, covering the major aspects needed to understand and work with the software.
  • Application-level understanding: Use the generated documentation to understand what the application does, how its workflows fit together, and how its technical implementation supports those capabilities.
  • Support for future engineering work: Use the documentation as a reference for enhancements, bug fixing, maintenance, onboarding, and other work on the existing codebase.
  • Specification-driven AI development: Refine the generated documentation into an agreed specification that can be used as structured input for future AI-assisted, specification-driven development.
  • Recommendations across phases: Relevant SDLC phases can provide evidence-based recommendations, while the dedicated Future Directions phase provides a broader view of potential next steps.
  • Review Repo: Use Review Repo for a broader review and synthesis of the generated SDLC documentation. It can work with a subset of phase outputs, so you do not have to provide every phase document.
  • Selective analysis and reruns: Run the phases you need and rerun individual phases when a result needs improvement, without automatically repeating the entire analysis.
  • Progressive results: View completed phase results as they become available while the remaining analysis continues, with the ability to stop an active analysis when needed.
  • Evidence-oriented analysis: The workflow combines repository intelligence, targeted research, phase-specific guidance, and repository inspection so generated documentation is grounded in the implementation rather than based only on surface-level code summaries.

2. Use the main repository as the input

  • Enter the repository's main Git clone URL, such as https://github.com/org/repo.git or the standard GitHub repository URL.
  • The current V1 repository acquisition flow is designed for the main/default repository and does not yet support GitHub tree URLs for branches or tags, such as /tree/v1.
  • If you need to analyse a particular branch or tag, use the repository's supported main URL for now; branch/tag URL support is planned for a later version.
  • Analysis inputs cannot be changed after analysis starts. Once you have submitted the API key, model selection, and repository, those inputs cannot be changed within the same analysis. If you need different inputs, start a new browser tab and begin a new analysis.

3. Start with an inexpensive model

  • You do not need a frontier model to get useful SDLC documentation; OpenRouter/free models can produce a meaningful baseline, particularly when the repository is reasonably structured.
  • The application uses repository intelligence, phase-specific research, common agent instructions, and phase/skill guidance to give the model structured evidence and a repeatable analysis process.
  • A stronger model can still produce better results on difficult repositories or phases, so model quality remains one factor in the final output.
  • Once you get a baseline, you can ask your coding agent to refine the documents, if need be.
  • If you use OpenRouter/free models, consider running only 2–3 phases at a time. Free models may be subject to provider request-per-minute limits, so running many phases simultaneously can increase the chance of rate-limit failures.
  • OpenRouter/free may route different turns to different available models. As a result, a single phase may be processed by different models across its turns, so results can vary between runs.
  • If you use OpenRouter/free, check your OpenRouter model settings and exclude the Nemotron Security model. It may classify the request instead of producing the expected analysis output, which can result in an empty phase result.

4. Model quality and cost can be compared phase by phase

  • A practical approach is to run a baseline with a free model, review the phases, and use a stronger model only where a result needs deeper reasoning or correction.
  • A complete 12-phase analysis can use up to approximately 3.7 million input and output tokens, with input tokens typically making up the largest portion. Actual consumption varies with the repository, selected phases, model, prompts, and analysis path.
  • Paid models can increase cost, but OpenRouter/free models can still provide a useful and reasonable baseline.
  • For the Vercel Next.js Commerce demonstration, a paid DeepSeek V4 Flash run through OpenRouter used approximately $0.10 across 141 requests, 3.27 mn tokens, with an observed cache hit rate of approximately 75.3%.
  • These figures are a demonstration snapshot rather than a fixed cost estimate; actual cost depends on repository size, selected phases, model, prompts, caching, and provider pricing.

5. All available SDLC phases can be run in parallel

  • All available SDLC phases can be selected and run in parallel.
  • When using OpenRouter/free models, running about 2–3 phases at a time is recommended because free-model providers may impose request-per-minute limits.
  • If you encounter provider rate limits with other models, reducing the number of simultaneous phases can also make failures easier to isolate and reduce simultaneous provider load.
  • You can rerun individual phases without repeating the entire analysis.

6. Current provider support

  • In the current V1 demo, the application directly supports OpenAI and OpenRouter.
  • Other model providers can be accessed through OpenRouter where their models are available, without requiring provider-specific integration in the application.

7. Treat the output as an evidence-based starting point

  • Reverse SDLC reconstructs documentation from an existing implementation; it does not know the original team's undocumented intentions.
  • The source repository remains the primary source of truth, while generated documentation is an interpretation that should be verified.
  • When reviewing a statement, ask: “Where in the repository does this claim come from?”

8. Review before using the documentation

  • Check business behavior, architecture, technology and dependency claims, user workflows, security observations, testing claims, assumptions, and recommendations.
  • AI can miss relevant code, oversimplify architecture, infer behavior incorrectly, or describe legacy behavior as intentional design.
  • If a result is not satisfactory, rerun that phase. If necessary, start a new browser tab and run the phase again.
  • If you refresh the page during your work, the Review Repo workflow may no longer have access to phase results from the previous session. You may need to rerun the phases you want to use as input for Review Repo.

9. Workspace and stopping analysis

  • If you need to stop because of unexpected token usage, cost concerns, incorrect inputs, or because you no longer want the analysis to continue, use Stop & Exit. Any completed work is retained up to the point at which the analysis is stopped.
  • If you realize that you entered incorrect input values, use Stop Analysis rather than allowing the analysis to continue. Work completed up to that point is retained.
  • Your OpenAI API key is not stored by the application. The server-side workspace created for an analysis is removed when you close the workspace using Stop & Exit.

10. Documenting an existing repository

  • Run a baseline: Start with an available inexpensive model rather than optimizing for maximum model capability immediately.
  • Review: Identify statements that are well supported, uncertain, speculative, incomplete, or incorrect.
  • Rerun: Improve weak phases individually instead of automatically rerunning everything.
  • Refine: Review and refine the generated documents before treating them as permanent project documentation.

11. Do not confuse current behavior with desired behavior

  • Reverse SDLC starts from what the software currently implements, so generated requirements and architecture may describe existing behavior even when that behavior is undesirable or incomplete.
  • When converting the output into future specifications, explicitly distinguish observed current behavior from intended future behavior.

12. Use Reverse SDLC for specification-driven development

  • Generate documentation from the implementation, review it, resolve contradictions and ambiguities, and refine it into a specification that represents the intended future system.
  • The resulting documentation can then serve as a structured input for subsequent development work, including AI-assisted specification or coding workflows.
  • If you install the application locally from GitHub, you can further customize the agent instructions and skill definitions used by individual phases to suit your repository, workflow, or documentation requirements.

13. When a result does not look right

  • First determine whether the problem is isolated to one phase rather than assuming the entire analysis has failed.
  • If the repository contains ambiguous, inconsistent, legacy, or undocumented behavior, human review may be required to determine the intended meaning.
  • If a phase produces an unsatisfactory result, rerun that phase rather than automatically repeating the entire analysis.

14. Important limitations

  • Reverse SDLC cannot guarantee that every generated statement is correct or complete.
  • The quality of the result depends on the repository, the available repository intelligence, the analysis instructions, and the model used.
  • Generated documentation should be reviewed before it is used for important technical, product, or business decisions.

15. Practical workflow

Use the main repository → Analyze → Review → Identify weak phases → Rerun selectively → Refine → Publish/use
  • Start inexpensively, spend additional model capacity only where it improves the result, and keep the source repository available for verification.
