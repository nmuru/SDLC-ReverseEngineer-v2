Using Reverse SDLC

A practical guide to getting useful, reliable documentation from an existing software repository.

1. What should I expect from this application?

Reverse SDLC helps you understand an existing software repository and turn what is already implemented into structured engineering documentation.

Depending on the phases you select, the output can help you understand:

  • Business purpose and product intent
  • Requirements and functional behavior
  • Architecture and technical design
  • Implementation details
  • Testing and validation
  • Future directions, gaps, and technical debt

The quality of the result depends on both the repository and the AI model being used. This application is intended to accelerate understanding and documentation, not replace engineering judgment.

2. Run a small group of phases at a time

Recommended: run about 3–4 phases at a time. Provider rate limits can prevent a larger request from completing. Free models may have tighter limits; as a practical example, a free model may not reliably accept more than 3 phases in one request.

If you need all phases, split them into several runs. This also makes it easier to identify and rerun a phase if one result needs improvement.

3. You do not need an expensive model to start

This application does not require a frontier model. You can use OpenRouter and free models to establish a useful baseline. OpenRouter can route requests to free models made available by different providers, including models such as Nemotron, LFM, Cohere, and others.

Some repositories may benefit from a larger or stronger model, including medium-sized models around the 32B class or comparable models.

A practical approach is:

  1. Start with an available free model.
  2. Review the generated documentation.
  3. Identify phases that are incomplete, ambiguous, or inaccurate.
  4. Rerun those phases using a stronger model if necessary.

4. AI can make mistakes

AI-generated documentation can contain mistakes, omissions, incorrect assumptions, or hallucinations. Reverse SDLC has not attempted to make the output perfect or eliminate every possible hallucination.

If you find an incorrect or hallucinated result, rerun that phase. You can also try the same phase with a better or paid model if the repository is complex or the result requires greater accuracy.

5. Review the output before using it as engineering documentation

If you are using Reverse SDLC to document an existing GitHub repository, review the generated documents before treating them as project documentation.

In particular, check business behavior, architecture descriptions, technology and dependency claims, assumptions about user workflows, security-related observations, testing claims, and future-development recommendations.

The source code remains the primary source of truth. The generated documentation is an interpretation of that source.

6. Documenting an existing repository

Step 1 — Run a baseline analysis

Start with the model that is readily available to you. You do not need to optimize for the strongest possible model immediately.

Step 2 — Review the generated phases

Look for statements that are clearly supported by the code, useful but requiring verification, too speculative, missing important information, or incorrect.

Step 3 — Rerun weak phases

Rerun phases that need improvement. You can use a stronger model for that phase rather than rerunning the entire analysis with a more expensive model.

Step 4 — Refine before publishing

If the generated documents are going to become permanent project documentation, review and refine them before publishing them to your repository or documentation system.

7. Using Reverse SDLC for spec-driven development

Reverse SDLC can also be useful when an existing repository is being used as the starting point for specification-driven development.

  1. Generate the documentation from the existing implementation.
  2. Review the generated documents.
  3. Ask your coding or specification agent to refine each document.
  4. Resolve contradictions and ambiguities.
  5. Confirm that the refined specification represents the intended future behavior.
  6. Use the refined specification as an input to subsequent development work.

This is particularly important when the existing implementation contains legacy behavior, incomplete features, workarounds, or technical debt.

8. Do not confuse current behavior with desired behavior

There is an important distinction between what the software currently does and what the software should do in the future.

Reverse SDLC starts from the existing implementation. Generated requirements or architectural descriptions may therefore describe behavior that exists today even if that behavior is not ideal.

9. Choosing a model

Consider starting with a free model when you are exploring the application, want a quick baseline, the repository is relatively straightforward, cost is important, or you want to compare model quality.

Consider a stronger model when the repository is large or complex, the architecture is difficult to infer, generated output contains significant ambiguity, a particular phase requires deeper reasoning, or the documentation will be used for important downstream engineering work.

10. When a result does not look right

Do not immediately assume that the entire analysis has failed. First determine whether the problem is isolated to a particular phase. If it is, rerun that phase. If the result is still poor, try a stronger model and compare the output.

If the repository itself contains ambiguous, inconsistent, or undocumented behavior, the AI may reasonably struggle to determine the intended meaning. Human review is especially important in those cases.

11. Keep the source repository available for verification

Generated documentation is much more useful when engineers can verify important statements against the source repository.

A useful review question: “Where in the repository does this claim come from?” If the answer is unclear, treat the statement as something that needs verification rather than established fact.

12. A practical recommended workflow

Analyze → Review → Identify weak areas → Rerun → Refine → Publish/use
Start inexpensively. Review the results. Spend additional model capacity only where it improves the result. Have a human or coding agent refine the documents before they become a formal specification or permanent project documentation.

13. Important limitations

Reverse SDLC cannot guarantee that every generated statement is correct. AI may misinterpret implementation details, infer behavior that is not explicitly present, miss relevant code, oversimplify complex architecture, describe legacy behavior as intentional design, or produce recommendations that require engineering judgment.

For these reasons, generated documentation should be reviewed before being used to make important technical or product decisions.

14. The most useful way to think about Reverse SDLC

Reverse SDLC is best viewed as a documentation and understanding accelerator. It can significantly reduce the effort required to understand an unfamiliar codebase, but it does not remove the need for engineering judgment.

Use the AI output to get from “I need to understand this repository.” to “I have a structured starting point that I can review, verify, and refine.”
