# Business-Requirements Phase Summary

The repository implements a shopper‑centric e‑commerce experience built on Next.js App Router with Server Components and Server Actions. The primary actor is the shopper, whose goals encompass product discovery, cart management, and content consumption within a defined system boundary that separates client‑side UI from server‑side Shopify integration.

**Product and domain intent** is explicitly documented in README.md: the template is a high‑performance, server‑rendered Next.js Commerce application focused on Shopify as the commerce provider, with the README noting that alternative providers (BigCommerce, Ecwid, Geins) can be swapped by forking and replacing the `lib/shopify` layer. The core domain revolves around a product catalog, shopping cart, checkout flow, and content pages. This intent is reinforced by the structure of user‑facing surfaces—`app/page.tsx` (home), `app/product/[handle]/page.tsx` (product detail), `app/search/page.tsx` (search and filtering), `app/[page]/page.tsx` (static content), and `app/search/[collection]/page.tsx` (collection browsing)—each designed to serve distinct shopper workflows.

**Representative workflows** emerge from the component and API structure. Shoppers browse products through the home page grid and product‑detail page, which combines a gallery, description, variant selector, and “Add to Cart” button (`components/product/variant-selector.tsx`, `components/cart/add-to-cart.tsx`). Adding to cart triggers `addItem` in `components/cart/actions.ts`, which calls Shopify mutations via `lib/shopify/index.ts` and persists the cart locally via `CartProvider` in `components/cart/cart-context.tsx` and a cookie set by `createCartAndSetCookie`. The cart is viewable in a modal (`components/cart/modal.tsx`) that displays items, totals, and action buttons (delete, quantity update, checkout). Cart state is managed locally and synced with Shopify; mutations such as `removeFromCart` and `updateCart` flow through `lib/shopify/mutations/cart.ts` and `lib/shopify/queries/cart.ts`. Search and filtering operate via `app/search/page.tsx` and related filter components (`components/layout/search/filter/`), presenting collection lists and faceted filter items that navigate to `app/search/[collection]/page.tsx`. Static content pages are fetched through `lib/shopify/queries/page.ts` and rendered with prose components (`components/prose.tsx`). The externally callable operation `app/api/revalidate/route.ts` enables cache invalidation after cart mutations, ensuring data consistency at the edge.

**State management** is centered on `CartProvider` and `useCart` in `components/cart/cart-context.tsx`, which holds cart items, totals, and actions to update the cart locally and sync with Shopify. The cart context initializes via `createCartAndSetCookie`, providing cookie‑based persistence across sessions. Product data, collections, and pages are fetched server‑side through `lib/shopify/index.ts` and its supporting query files (`queries/product.ts`, `queries/collection.ts`, `queries/page.ts`, `queries/menu.ts`), producing strongly typed responses defined in `lib/shopify/types.ts`. Type guards in `lib/type-guards.ts` and utilities in `lib/utils.ts` provide validation guards for Shopify responses.

**Validation and business rules** are supported by the type‑system and mutation pipeline. Shopify GraphQL mutations for cart operations are defined in `lib/shopify/mutations/cart.ts` and queried through `lib/shopify/queries/cart.ts`, with fragments (`lib/shopify/fragments/cart.ts`) ensuring consistent shape extraction. The revalidation endpoint (`app/api/revalidate/route.ts`) exposes a mutation‑protected route that triggers cache revalidation using the `SHOPIFY_REVALIDATION_SECRET`. Type safety is maintained across the dependency chain: `lib/shopify/index.ts` imports from `lib/shopify/mutations/cart.ts`, `lib/shopify/queries/cart.ts`, `lib/shopify/queries/collection.ts`, `lib/shopify/queries/menu.ts`, `lib/shopify/queries/page.ts`, and `lib/shopify/queries/product.ts`, which in turn import fragments from `lib/shopify/fragments/`. Client components import from `components/cart/actions.ts`, `components/cart/cart-context.tsx`, and related UI modules, forming a unidirectional data flow from server‑fetched data to local state to UI updates.

**Dependencies and external integrations** are anchored on the Shopify GraphQL API, encapsulated in `lib/shopify/index.ts` and its query/mutation files. Environment variables `SHOPIFY_STORE_DOMAIN`, `SHOPIFY_STOREFRONT_ACCESS_TOKEN`, and `SHOPIFY_REVALIDATION_SECRET` inject credentials at deployment (Vercel), while `SITE_NAME` and `VERCEL_PROJECT_PRODUCTION_URL` configure deployment metadata. The component dependency graph—spanning `app/layout.tsx` → `app/globals.css`, `components/carousel.tsx` → `components/grid/tile.tsx`, `components/opengraph-image.tsx` → `components/icons/logo.tsx`, and the `lib/shopify` import chain—maps the technical scaffolding that enables the business workflows.

**Notable uncertainties** merit brief acknowledgment. The README describes a provider‑abstraction model where `lib/shopify` can be swapped, yet the repository contains only Shopify‑specific code; it is unclear whether a generic interface or shared schema exists to facilitate easy substitution beyond the noted fork‑and‑replace approach. The `test` script runs only `prettier:check`, indicating no configured unit‑test or integration‑test framework; the absence of testing libraries may limit visibility into code‑quality assurance. The exact GraphQL schema version and `SHOPIFY_GRAPHQL_API_ENDPOINT` are not detailed in the supplied intelligence, leaving the precise API contract ambiguous. Finally, the README references Next.js Commerce v1 while the codebase appears to be v2 (App Router–based); the relationship between the versions and any migration path is not clarified.

In sum, the repository delivers a shopper‑focused e‑commerce experience with clear workflows for product discovery, cart management, search, and content consumption, grounded in a Shopify‑centric data layer and Vercel‑hosted deployment. The strongest evidence supports a bounded system where server‑side data fetching, local cart state, and mutation‑driven synchronization define the core business behavior, while uncertainties surround provider‑abstraction generality, testing coverage, API schema specifics, and version lineage.
